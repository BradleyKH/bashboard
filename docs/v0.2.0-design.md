# Bashboard v0.2.0: design spec

This spec covers nine features for v0.2.0. It is written against `docs/design.md` and cites
its sections the same way the code does ("4.8" means docs/design.md section 4.8). Each feature
names the design doc sections it touches; as a feature lands, its text folds into those
sections and the design doc's milestone list (section 11) gains a v0.2.0 entry.

| # | Feature | Touches |
| --- | --- | --- |
| 1 | Waiting reason on cards and title strips | 3.3, 4.4, 4.6, 4.7, 7 |
| 2 | Jump to the next terminal that needs you | 4.5, 4.7 |
| 3 | `done` and `failed` for long shell commands | 4.6, 4.8, 4.10, 8 |
| 4 | Worktrees in the Repo section | 3.8, 3.9, 4.6, 7 |
| 5 | Command palette | 4.5, 4.6 |
| 6 | Drag paths onto terminals | 4.4, 4.12, 4.13, 4.14, 4.15 |

Section 10 of this spec collects the keybinding changes, section 11 the settings, section 12 the
tests, and section 13 a suggested phase order.

## 1. Waiting reason

A terminal in `waiting` says why. Claude Code's `Notification` hook carries a `message` ("Claude
needs your permission to use Bash"), which the receiver already parses (3.3) and emits on
`sessions://hook`, but nothing displays it.

**Core.** `HookOverlay` gains `waiting_message: Option<String>`, set from the `message` of the
`Notification` that set `waiting`, trimmed and cut at 200 characters, and cleared whenever the
overlay's status leaves `waiting`. The roster payload (section 7) gains `waitingReason: string |
null`, present only while the merged status is `waiting`. Keeping it in the overlay rather than
the front end means a page reload, and external sessions, still show it.

**Front end.** Wherever a `waiting` dot shows, the reason shows with it:

- **Pane card** (4.6): a line under the title in the accent color, in place of the folder path
  while waiting, one line with an ellipsis, full text on hover.
- **Title strip** (4.4): the status dot's tooltip only; the strip's text is unchanged, since a
  reason would crowd a narrow pane.
- **Tab** (4.10): the tab's tooltip lists each waiting terminal's title and reason.
- **External sessions** (4.6): the row shows the reason under the folder, the same as a card.

A `waiting` with no message (older Claude Code, or a notice without one) shows "Waiting for
you". The reason is never sent to the backdrop.

## 2. Jump to the next terminal that needs you

`nextAttention` (Ctrl+Shift+L, section 10) focuses the next terminal that needs you, across all
tabs.

**Order.** Every `waiting` terminal, oldest `statusChangedAt` first, then every `done` or
`failed` terminal (section 3), oldest mark first. Terminals that rang the bell without a status
are not included; their pulse stays the cue.

**Cycling.** When the focused pane is in the list, the jump goes to the entry after it, wrapping;
otherwise to the first entry. `waiting` does not clear on focus, so repeated presses walk the
whole list instead of returning to the same terminal. `done` and `failed` clear on focus (4.8),
so they drop out as they are visited.

**Reaching the pane.** The jump switches to the pane's tab if needed and focuses it. A collapsed
terminal expands as clicking its card does (4.3). A zoomed pane (4.2) in the target tab unzooms
first. An empty list shows a toast, "Nothing needs you".

The ordering is a pure function in its own module (`attentionQueue.ts`) over the pane ids,
statuses, change times, tabs, and the focused id, so it is unit-tested without the workspace.

## 3. `done` and `failed` for long shell commands

A shell command that runs at least `terminal.doneAfterSeconds` (default 30, 0 turns it off) and
finishes while its terminal is not being looked at (the 4.7 definition) marks the terminal `done`,
or `failed` when it exited nonzero. This brings `docker compose up`, long builds, and test runs to
the same quiet signal Claude's `Stop` gives.

- **Timing.** Measured from OSC 133 `C` to `D`. Only shells that emit OSC 133 qualify: Git Bash
  with the `~/.bashrc` lines (3.14). The activity sweep is not used, since it counts background
  jobs and reports up to 2 seconds late; PowerShell and Command Prompt terminals therefore never
  get a command mark.
- **Failure.** `D` with a nonzero exit code marks `failed`, except 130 (interrupted with Ctrl+C),
  which marks nothing. `D` with no exit code marks `done`.
- **Bound sessions win.** While a Claude session is bound, its status resolves first (4.8) and
  command marks are not set. When `claude` itself exits after a long run, its `D` is an ordinary
  long command.
- **Clearing.** A mark clears the way `done` does: when the terminal becomes the pane being
  looked at. A command mark also clears on the next `C`, and a newer mark replaces it.
- **Quiet.** Like `done`, `failed` raises no attention: no pulse, taskbar flash, or panel peek.

**Display.** `failed` is display state beside `done` (not a roster status). Its dot is a still
cross in the error color, where `done` is a still check mark. The tab dot's urgency order (4.10)
becomes `waiting`, `failed`, `done`, `working`, `idle`, and the dashboard's group headers follow it.
The card's time-since label counts from the mark.

**Model.** `DoneTracker` (`doneStatus.ts`) holds marks of two kinds, `session` (the existing
`Stop` mark) and `command`, each with `failed: boolean`; `command` marks ignore the session
binding rules. `Pane` records the `C` time, which it already sees in `onOsc133`, and reports the
duration and exit code on `D`.

## 4. Worktrees

The Repo section (4.6) lists the repo's worktrees, and clicking one shows how it compares with
the primary branch and its upstream, with actions to open it or delete it.

### 4.1 List

Shown under the pins when the focused repo is a git repo with two or more worktrees. Every
worktree of the repo's common git dir is listed, the main worktree first, then the rest by
folder name. The worktree of the focused pane is highlighted. Each row shows:

- The folder name, with the path on hover (shortened as other dashboard paths are).
- The branch, or the short hash when detached.
- Ahead and behind counts against the primary branch (4.3), such as "3 ahead, 12 behind",
  omitted when both are zero.
- A badge: **Merged**, **Probably merged**, **Locked**, or **Prunable** (folder missing), in that
  priority. The main worktree never shows Merged.
- The folder button and the Open menu that every dashboard row has (4.6).

Worktree rows join the panel's keyboard rows (4.6), so Enter expands or collapses one as a click
does, and the detail's action buttons are reached with Tab.

The list loads with `git_worktrees(root)` when the section shows a repo, and reloads on
`git://changed` for any of the repo's roots (fetches and branch moves change refs in the common
dir, which every watcher covers) and after the app runs a fetch (section 7). It does not follow
the Repo section's 3 second re-read, since its counts cost a `rev-list` per worktree.

### 4.2 Detail

Clicking a row expands it in place (clicking again, or another row, collapses it) and loads
`git_worktree_detail(path)`:

- **Head.** The newest commit's subject, short hash, and relative time.
- **Against primary.** "3 ahead, 12 behind `origin/main`", plus the merged state in words:
  "Merged: every commit is in `origin/main`", "Probably merged: `origin/feature-x` was deleted on
  the remote", or "Not merged".
- **Upstream.** Its name with ahead and behind, "No upstream", or "Upstream deleted on the
  remote".
- **Working tree.** "Clean", or the count of staged, changed, and untracked files.
- **Actions.** Terminal, Files, Git, and Editor (as the Open menu), Open in File Explorer, and
  Delete.

### 4.3 Primary branch and merged state

`git_primary_branch(root)` resolves the branch the worktrees are compared against:

1. `primaryBranch` for the repo in `repos.json` (section 7), when set and it exists.
2. The branch `refs/remotes/origin/HEAD` points at.
3. The first of `dev`, `develop`, `main`, and `master` that exists as a local branch or on
   `origin`.

The comparison ref is `origin/<primary>` when it exists, so "merged" means merged on the remote,
and the local `<primary>` otherwise. `repos.json` gains the optional `primaryBranch` per repo,
set from the Repo section's header menu ("Compare worktrees with...", listing local branches).

Merged state, from local git only:

- **Merged**: `merge-base --is-ancestor <branch> <comparison>` succeeds. This includes a branch
  with no commits of its own, which is right for the question being answered (deleting it loses
  nothing).
- **Probably merged**: not an ancestor, and the branch's configured upstream is gone
  (`for-each-ref --format=%(upstream:track)` reads `[gone]`). This is how a squash-merged PR on
  GitHub or Bitbucket looks after a fetch with prune. It is as current as the repo's last fetch,
  which background fetch (section 7.2) refreshes while a Git pane is open on the repo.
- **Not merged** otherwise.

### 4.4 Delete

Delete asks first in a confirm dialog that names the folder and branch, with a checkbox "Also
delete branch `<name>`". The checkbox is checked and enabled only when the state is Merged; for
Probably merged it is disabled with the note "Squash-merged branches need `git branch -D` in a
terminal", since `branch -d` refuses them and the app never runs `-D`.

`git_worktree_remove(root, path, deleteBranch)` runs `worktree remove <path>` (never `--force`),
then `branch -d <branch>` when asked. It is refused, with the reason inline in the detail, when:

- the worktree is the main worktree, locked, or not clean (any staged, changed, or untracked
  file);
- any pane in the app (terminal working directory, or another kind's folder) is inside it, since
  a shell's working directory holds the folder open on Windows and would fail the removal
  halfway; the message names the panes;
- an external Claude session's working directory is inside it.

A failure from git itself (an editor holding a file, for example) shows git's output, as a failed
commit does (4.13). A branch delete that fails after the worktree is removed says so and leaves
the branch.

### 4.5 Core

New commands in `git.rs` (3.9), all reads with `GIT_OPTIONAL_LOCKS=0`:

| Command | Runs |
| --- | --- |
| `git_worktrees(root)` | `worktree list --porcelain -z`, `for-each-ref` for each branch's upstream and track, and `rev-list --left-right --count` against the comparison ref per worktree |
| `git_worktree_detail(path)` | `status --porcelain=v2 --branch -z` and `log -1` in that worktree, plus the merged state |
| `git_primary_branch(root)` | The resolution in 4.3 |
| `git_worktree_remove(root, path, deleteBranch)` | The removal in 4.4 (a write; no optional-locks override) |

The porcelain parser and the merged-state derivation are pure functions with unit tests.

## 5. Command palette

`openPalette` (Ctrl+Shift+P) opens one filterable list over everything the app can open or do.
The layout picker keeps its own action, `openLayout`, on Ctrl+Shift+R (section 10).

**Items**, each with a category shown at the right of the row:

| Category | Items | Enter |
| --- | --- | --- |
| Pane | Every pane in every tab, by title, with its tab's name as detail | Focuses it as clicking its card does |
| Tab | Every tab by name | Switches to it |
| Favorite | Every favorite | Opens it as the favorites picker does |
| Layout | Every layout | Opens it as a new tab |
| Pin | The focused repo's pins | Opens it as clicking it in the Repo section does |
| Worktree | The focused repo's worktrees | Opens a terminal there as a split |
| Action | Every keymap action that makes sense without a key context, with its chord | Runs it as its key would |

Ctrl+Enter opens a Favorite or Worktree collapsed, as the pickers do. Actions left out are those
that act on terminal text or need a number (`copy`, `paste`, `newline`, `switchToTab`); tabs are
items instead. Action labels come from `helpModel.ts`, so the palette and the F1 guide never
disagree, and chords come from the live keymap, so overrides show.

**Matching.** Fuzzy over the label (consecutive and word-start matches rank higher), then the
detail. With an empty query the list shows the session's most recent picks first, then the
categories in the table's order. A leading `>` limits the list to actions, as in VS Code.

**Mechanics.** The existing `Picker` (`picker.ts`) gains an optional category and hint per item
and a pluggable matcher, so the favorites, layout, and profile pickers keep working unchanged.
The palette's item building and ranking live in their own pure module (`paletteModel.ts`).
Closing the palette refocuses the pane that had focus before running the choice, so actions apply
to it.

## 6. Drag paths onto terminals

Dropping files onto a terminal inserts their paths, as a bracketed paste without Enter, and
focuses that terminal.

**Sources.**

- **File Explorer.** Tauri's webview drag-drop events (`onDragDropEvent`), which the window
  receives by default (`dragDropEnabled`). The drop's physical position is divided by
  `devicePixelRatio` and hit-tested with `elementFromPoint`.
- **Files pane** rows (4.12), files and folders.
- **Search pane** match rows and file group headers (4.14): the file's path, without a line
  number, since `path:line` is not a valid path for a shell.
- **Git pane** file rows in Staged and Changes (4.13). A deleted file's path is still inserted.

In-app drags use the same pointer-drag pattern as favorite rows (`attachBodyDrag`), with the
same threshold, so a click still selects a row, opens a diff, or previews a match. A small
ghost with the file name follows the pointer.

**Targets.** An expanded terminal highlights while a path is over it, and dropping there inserts
the paths. A scratch pad (4.15) takes the same text at its caret. Nothing else is a target; a
drop elsewhere does nothing. Dragging over a tab switches to it after half a second, as pane
drags do (4.10).

**Text.** One function, `pathInsertText(paths, targetRepoRoot, profile)` in `filesRouting.ts`,
formats every path insertion, including the Files pane's Insert path menu item:

- Each path is relative to the target terminal's repo (3.8) with forward slashes when it is
  inside it, and absolute otherwise. A path equal to the root is `.`.
- Absolute paths use forward slashes (`C:/Users/...`) in Git Bash, PowerShell, and Claude Code,
  and backslashes in Command Prompt.
- A path holding anything outside `A-Z a-z 0-9 . _ - / : @ +` is quoted for the target's profile:
  single quotes in Git Bash (a `'` written as `'\''`) and PowerShell (`''`), double quotes in
  Command Prompt.
- Several paths are joined by spaces, and the text ends with a space so typing continues.

**Out of scope.** Dropping onto a Files pane (copying files in), dragging between Files panes
(Move to covers it), and dragging out of the app to File Explorer.

## 7. Fetch, pull, push, and background fetch

### 7.1 Git pane

The branch row (4.13) gains three buttons:

- **Fetch** runs `fetch --prune`. Enabled whenever the repo has a remote.
- **Pull** runs `pull --ff-only`. Enabled while the branch has an upstream and is behind it, and
  shows the behind count. A diverged branch fails with git's message; merging or rebasing is left
  to a terminal.
- **Push** runs `push`. With no upstream it reads **Publish** and runs `push -u <remote>
  <branch>`, where the remote is `origin`, or the only remote; with several remotes and no
  `origin` it is disabled with a tooltip. Enabled while ahead of the upstream or unpublished.
  Disabled on a detached HEAD.

The app never force pushes. A rejected push shows git's message, so after Undo commit on a pushed
commit (4.13) the force push stays in a terminal, as the undo's warning already says.

While one runs, all three show it and are disabled, and the commit box stays usable. A failure
shows git's output in the same place as a failed commit, and the branch row's last fetch time
("Fetched 3 min ago") updates on success.

### 7.2 Background fetch

Every `git.autoFetchMinutes` (default 5, 0 turns it off), the core fetches each repo that has an
open Git pane, once per common git dir, so Git panes on several worktrees of one repo share a
fetch. Panes of other kinds never trigger a fetch. A Git pane opening on a repo whose last fetch
is older than the interval fetches at once.

- Pauses while the window is hidden or minimized, as the backdrop does (6.4), and catches up on
  show when a fetch is overdue.
- Runs with `GIT_TERMINAL_PROMPT=0` and `GCM_INTERACTIVE=never`, so a background fetch never
  opens a credential prompt, and is killed after 60 seconds (an SSH key with a passphrase and no
  agent would otherwise hang it).
- A failure is quiet: the Git pane's last fetch label reads "Fetch failed" with git's output as
  its tooltip. Background fetch skips a repo for the rest of the session after three failures in
  a row; a manual Fetch resets that.

Manual Fetch, Pull, and Push also set `GIT_TERMINAL_PROMPT=0`, since there is no terminal to
prompt in, but allow Git Credential Manager's own window. Fetches move refs, so the existing
watcher's `git://changed` refreshes the Git pane and the worktree list with no extra wiring.

### 7.3 Core

| Command | Runs |
| --- | --- |
| `git_fetch(root, background)` | `fetch --prune`, with the background environment when `background` |
| `git_pull(root)` | `pull --ff-only` |
| `git_push(root)` | `push`, or `push -u <remote> <branch>` with no upstream |
| `git_last_fetch(root)` | The time and outcome of the last fetch the app ran for that common dir |

The background scheduler lives in the core (`git_fetch.rs`), keyed by common dir. The front end
tells it which roots have open Git panes (`git_fetch_roots(roots)` whenever a Git pane opens,
closes, or changes repo), so the core needs no knowledge of the layout.

## 8. Keybinding editor

Keys are changed in the app, in the F1 shortcut guide, which becomes editable. Assigning a chord
that another action already uses moves it to the new action in one step, after saying which
action gives it up, and the move can be undone from the notice that follows.

The guide is the right home because it already lists every action by section with its live
chords (`helpModel.ts`); editing there means the place a user looks a key up is the place they
change it. The settings dialog gains a Keyboard section holding one button, Edit keyboard
shortcuts, which opens the guide, and the Open settings.json note stops saying keybindings are file-only.

### 8.1 Rows

The guide keeps its sections and labels. An action that takes an argument shows one row per
argument: Move focus left, right, up, and down; Resize pane the same; Go to tab 1 through 8.
Each `sendInput` binding gets its own row labeled by its input (Shift+Enter's reads "Claude Code
newline"); new `sendInput` bindings are still written in the file, since they need text the
guide has no field for. The "In pickers and bars" section stays read-only. Every action in the
name list has a row, including one with no default, so any action can be given a key.

Each row shows its chords as keycaps, then:

- **Add** (a `+` after the last keycap) records another chord for the action.
- **A keycap**, clicked, records a replacement for that chord; its `x` removes it.
- **Reset**, shown only while the row differs from the defaults, restores its default chords.

A row that differs from the defaults has an accent dot by its label. A row with no chord reads
"No key", dimmed. A filter field at the top matches labels, and the Find by key button beside it
records one chord and scrolls to the row that owns it, or says "Not bound: reaches the shell".

### 8.2 Recording

Recording turns the keycap (or Add) into a field reading "Press keys". It listens for `keydown`
in the capture phase, ahead of `keys.ts`, so pressing a bound chord records it instead of
running it. Modifiers alone keep it waiting and show as they are held. Escape, or a click
elsewhere, cancels.

A recorded chord is checked before anything is saved:

| Chord | Result |
| --- | --- |
| A printable key with no modifier or with Shift alone; Escape, Enter, Tab, or Backspace with no modifier | Refused inline ("Shift+A would stop typing A"), still listening |
| Already on this action | "Already bound here", nothing changes |
| Unbound and not a shell key | Saved at once |
| Unbound, but the shell or Claude Code uses it | Saved at once, with a dimmed note (below) |
| Bound to another action | The move strip (8.3) |

The shell-key list is short and lives with the other rules: Ctrl+A, E, K, U, W, R, L, D, and
Ctrl+Left and Ctrl+Right among them, each with a few words on what it does in bash. A row holding
one shows a dimmed note under it, such as "Ctrl+R no longer reaches bash's reverse search", for as
long as the binding stands; there is no prompt. The list is a courtesy, not a guarantee; an
unlisted chord gets no note.

### 8.3 Moving a chord from another action

When the recorded chord belongs to another action, the field holds it and a strip opens under
the row:

```
Ctrl+Shift+D runs "Pause or resume the background animation". Move it here?   [Move] [Cancel]
```

If the move would leave that action with no key, the strip adds "It will have no key." so the
cost is visible before the choice. Enter moves, Escape cancels, and pressing a different chord
records that one instead, which is how a user backs out into a free chord without starting over.

Move is a single write: the chord leaves the other action and joins this one. Then:

- The other action's row flashes once, in place, with the chord shown struck through for the
  length of the flash, so the user sees what it lost without hunting for it.
- A notice at the bottom of the dialog reads "Ctrl+Shift+D moved from Pause or resume the
  background animation", with **Undo** and, when that action has no key left, **Assign a key**,
  which scrolls to its row and starts recording there. The notice stays until the next edit or
  10 seconds, whichever is first.
- **Undo** is a single write that puts both rows back as they were.

Reset follows the same rule. Resetting a row whose default chord another action now holds opens
the strip for that chord ("Ctrl+Shift+D runs Split along the longer side. Move it back?"); with
several, the strip lists them all and Move takes them all. Cancel resets nothing.

**Reset all**, in the dialog's footer, confirms first ("Remove every custom key and use the
defaults?"), empties the file's `keybindings` array, and shows the same notice with Undo.

### 8.4 Writing

The dialog never writes the merged keymap. It sends edits to a new command,
`settings_keybindings_edit(ops)`, which applies them to the raw `keybindings` array in
settings.json and keeps everything else in it: the user's other entries, their order, and entries
the loader rejected, so a typo in one entry is not silently deleted by an edit to another.

| Op | Effect on the array |
| --- | --- |
| `bind(keys, action, args)` | Removes the entries for `keys`, then adds `{ keys, action, ...args }` unless the default for `keys` is exactly that |
| `unbind(keys)` | Removes the entries for `keys`, then adds `"action": "unbound"` when `keys` has a default |
| `reset(keys)` | Removes the entries for `keys` |

Keys match through `normalize_chord`, so `Shift+Ctrl+L` in the file is the entry for
`ctrl+shift+l`. A move is one `bind`, since a chord has one action. Undo sends the ops the dialog
computed from the live keymap before the move. One call is one read-modify-write under the
settings write lock, through `settings_edit`, so comments outside the array survive; the array
itself is rewritten whole, one entry per line, and comments inside it are not kept.

The dialog does not update itself after a save. The watcher's `settings://changed` rebuilds the
keymap and re-renders the dialog, the same path a hand edit takes, so the file stays the single
source of truth and an edit made in an editor while the dialog is open shows up in it. A save
that fails leaves the rows as they were and shows the error in the notice.

**Modules.** `keybindingEdit.ts` is pure: the per-argument row list, the refusal rules, the
shell-key list, conflict detection against the live keymap, and the ops (and their inverses)
for add, replace, remove, move, and reset. `keybindingRecorder.ts` is the capture field, and
`helpDialog.ts` gains the edit controls. On the Rust side, op application is a pure function over
the parsed array in `settings.rs`, with `settings_edit` doing the write.

## 9. Expand the file preview

A Files pane's preview (4.12) can take the whole pane, for reading a long markdown file or log
without the list beside it. This is separate from pane zoom (4.2), which fills the tab with the
pane; the two combine into a full-window reader.

**Button.** The preview toolbar gains an Expand preview button after the − and + zoom buttons,
on every text preview (markdown, plain text, and read-only code) but not the binary or too-large
view. Its icon is a side panel with a left-pointing arrow, distinct from the title strip's zoom
icon, since both are on screen at once and act at different scopes. While the preview is
expanded the icon becomes the matching show-panel arrow and the button reads Show file list.

**Expanded.** The list, its breadcrumb, and the divider hide, and the preview fills the pane. The
toolbar shows the file's name, since the breadcrumb that located it is hidden. Everything inside
the preview works as before: find, zoom, the Edit toggle, editing and saving, and relative
markdown links, which open the linked file in the same pane and keep it expanded.

**Showing the list again.** Either of:

- The button.
- Esc anywhere in the preview, including the text editor, when nothing nearer takes it: an open
  find bar closes first (4.12), so with the bar open it takes two presses.

The list returns at the divider position it had, with the previewed file selected and the list
focused, so Up and Down browse on from there. Showing a folder in the pane (a pin, `bb open` on a
folder, 3.13) also brings the list back; selecting a file the same way keeps the preview
expanded.

**Restore.** The Files pane's saved state (section 7) gains `expanded?: boolean`, so a restored
workspace or a saved layout reopens as it was left. A pane restored expanded whose file is missing
shows the list.

## 10. Keybindings

| Keys | Action | Change |
| --- | --- | --- |
| Ctrl+Shift+P | `openPalette` | New action, taking over the chord |
| Ctrl+Shift+R | `openLayout` | The layout picker's chord |
| Ctrl+Shift+L | `nextAttention` | New action |
| Ctrl+Shift+D | `toggleBackdrop` | Pause or resume the animation |

`nextAttention` sits on L because it is right hand home or top row on both QWERTY (home) and
Dvorak (top); chords match the typed character (`keymap.ts`), not the physical key. A user's own
`keybindings` entries still layer on top (4.5). The release notes name the three moved chords
and point to the editor (section 8) for anyone who wants one back.

Each new action follows the checklist in CLAUDE.md: `keymap.ts` (type, name list,
`DEFAULT_KEYBINDINGS`), `default_keybindings()` in `settings.rs`, `isHandled` in `keys.ts`,
`Workspace.dispatch`, `helpModel.ts`, and the 4.5 table. An action that takes an argument also
needs its per-argument row labels in `keybindingEdit.ts` (8.1).

## 12. Testing

Following section 10 of the design doc: pure models in Vitest, the core against temp folders in
Rust.

- **Vitest.** `attentionQueue` (order, cycling past the focused pane, empty list);
  `DoneTracker` command marks (threshold, exit codes 0, 1, and 130, clearing on focus and on the
  next `C`, bound sessions suppressing them); `paletteModel` (item building, excluded actions,

## 13. Suggested phases

Ordered so each phase ends with a usable app and later phases build on earlier ones. File overlap
is noted because it decides what can run in parallel.

1. **Attention.** Waiting reason (1), long-command `done` and `failed` (3), then jump to next
   (2), which orders by both. Touches `hooks.rs`, `roster.rs`, `sessions.ts`, `doneStatus.ts`,
   `pane.ts`, `paneCard.ts`, `titleStrip.ts`, `tabItem.ts`, `sessionRow.ts`, `workspace.ts`,
   `keymap.ts`, `keys.ts`, `settings.rs`, `settings.ts`. The keybinding moves (10) belong here,
   since `nextAttention` takes Ctrl+Shift+L.
2. **Git remote.** Fetch, pull, push, and background fetch (7). Touches `git.rs`, a new
   `git_fetch.rs`, `gitApi.ts`, `gitPane.ts`, `settings.rs`, `settings.ts`, `settingsDialog.ts`.
   Independent of phase 1 apart from the settings files.
3. **Worktrees.** (4). Touches `git.rs`, `workspace.rs` for `primaryBranch`,
   `repos.ts`, `repoSection.ts`, a new worktree row and detail. Needs phase 2's fetch for
   Probably merged to stay current, though it works without it.
4. **Drag paths.** (6). Touches `filesRouting.ts`, `fileRow.ts`, `searchResultsList.ts`,
   `gitFileList.ts`, `scratchPane.ts`, `workspace.ts`, a new drop controller. Independent of
   phases 2 and 3; can run beside them.
5. **Palette.** (5). Touches `picker.ts`, a new `paletteModel.ts`, `keymap.ts`, `helpModel.ts`,
   `workspace.ts`. Last, since its Pin and Worktree items need phase 3.
6. **Keybinding editor.** (8). Touches `helpDialog.ts`, `helpModel.ts`, a new `keybindingEdit.ts`
   and `keybindingRecorder.ts`, `settingsDialog.ts`, `settings.rs`, `settings_edit.rs`, and
   `lib.rs` for the command. Needs phase 1's new actions to list them, and shares `helpModel.ts`
   with phase 5, so it follows the palette or runs beside phases 2 to 4.
7. **Expand the file preview.** (9). Touches `filesPane.ts`, `filePreview.ts`, `previewFind.ts`
   for Esc's order, and `savedWorkspace.ts`. Front end only and independent of every other phase,
   so it can run beside any of them.
